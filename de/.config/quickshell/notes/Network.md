# Network

`Network.qml` — `Picker`-based Wi-Fi + VPN menu (`Super+R` `N` / `qs ipc call network toggle`), replacing the floating kitty running nmtui. **This is also where the VPNs live** — a bottom-left `Vpn` card and then a separate VPN menu both came and went, because this menu already lists every tunnel and a second surface for the same rows is a second thing to keep honest. Non-obvious bits: (1) **every tunnel is an NM profile.** The lab `~/VPNs/*.ovpn` configs used to be run by `scripts/vpn-manager.sh` as a bare root `openvpn --daemon` NM knew nothing about; that needed a doas rule to start one and a *second* doas rule to kill one, scraped the profile's state out of `pgrep`+`/proc/<pid>/cmdline`, and surfaced as an *externally connected* `tun0`. When the kill rule didn't match, `disconnect` failed silently, `connect` stacked a second daemon, two tunnels ran at once on two tun devices — and each rejected `doas` counted as a failed login until the account locked for ten minutes. They are now imported (`nmcli connection import type openvpn file <f>`, which `nmcli general permissions` allows this user) and are ordinary NM connections: one code path, up/down by UUID, state from the snapshot the menu already takes, **no daemon, no script, no doas rule, nothing to scrape**. An `~/VPNs/*.ovpn` NM hasn't been given yet is **imported automatically** while the menu is open (`pendingImports` matches files against NM profiles by the name NM would give them, so an imported file is never handed over twice), which keeps "drop a lab config in `~/VPNs`" as the whole workflow. **The VPN section is a MIRROR of that directory** (plus the always-on tunnels), and it covers both kinds: **`*.ovpn` imports as openvpn, `*.conf` as wireguard** (`nmcli connection import type wireguard`), so a temporary wg config is dropped in the same place as a lab config. A file with no profile is imported, a profile whose file **changed** is deleted and re-imported, and a `type=vpn` profile with no file behind it is **deleted** — either the registry (`~/.local/state/quickshell/vpn-sources.json`) remembers the file it came from and that file is gone, or nothing has ever heard of the profile and no file would produce its name. That second case is what used to leave permanent garbage in the menu: a profile imported before the registry existed, or by hand, is in no registry to age out of. The change check is a **sha256 of the file**, recorded in the registry at import (`sha256sum` rides in the same listing poll). Name matching alone is not enough and this is not theoretical: HTB reissues a config under the same filename pointing at a new server, so `HTB-TCP.ovpn` said `dedivip-4` while the profile NM kept serving still said `dedivip-3` — every connection through the menu timed out while the very same file worked from a terminal, which is the confusing shape this takes. An entry with no stored hash predates the check; `adoptSources` stamps one on the next pass rather than re-importing on a guess. Consequence worth knowing: **an OpenVPN profile you created by other means, for a config that does not live in `~/VPNs`, will be removed** — put its name in `ALWAYS_ON` to exempt it. A WireGuard profile is only ever removed when the registry itself imported it and its file is gone — an **untracked** wireguard profile is left alone however it got there, because it holds a private key that may have no other copy, whereas an openvpn profile can always be rebuilt from its file. For the same reason a wireguard import is a bare `con import` with **no** `con mod` chained on: unprivileged, that drops the key it just stored. A wg tunnel takes its routes from `AllowedIPs`, so if one carries `0.0.0.0/0` and you want it split, that is a one-off `doas nmcli con mod <uuid> ipv4.never-default yes`. Both halves are gated on `filesSeen`, a listing that actually succeeded, so an unreadable `~/VPNs` can never read as "delete everything". **The import also sets `ipv4.never-default`/`ipv6.never-default` on the new profile, in the same command** — HTB pushes `default via <tun gw> metric 50`, which outranks the Wi-Fi default (metric 600), so without it every packet including DNS goes down a tunnel that carries no general internet and the machine drops off the network the instant a lab connects. `never-default` discards only that default; the lab subnets it also pushes (10.10.x, 10.129.x, 10.13.37/38) keep their routes. These are lab configs by definition, so split tunnel is the policy. The UUID comes from the import's own stdout, never a name lookup, and stdout is reprinted so the registry's own UUID match still sees it. The import goes through the same `run()` queue as user actions — two nmcli writes at once, or an import stomping the status line mid-connect, is the only way it could be worse than the manual step — and **three guards** keep it from making duplicate profiles, each answering a different question. (a) `importTried`, cleared on open: stops a file NM refuses from retrying every 5s and owning the status line, while still letting it succeed on the next open once the plugin is there. (b) `importDone`, never cleared: `nm.refresh()` is asynchronous, so for a second or two after an import `conns` still lacks the new profile — close and reopen the menu in that window and the name match says "missing" again. (c) `nmSeen`: **no import before the first nmcli snapshot has landed.** The file listing and the snapshot are independent polls and the listing usually wins, so with `conns` still empty every profile NM already has looks un-imported. That one produced exactly one duplicated profile per cold start — the first file in the list — because the import's own refresh corrected the snapshot before the next file was considered. The openvpn plugin's descriptor is at **`/usr/lib/NetworkManager/VPN/nm-openvpn-service.name`** (not `lib64`). Needs **`net-vpn/networkmanager-openvpn`**; without it `con import` fails with `unknown VPN plugin`. (2) The homelab tunnel — the NM `wireguard` profile, from the root-only `/etc/wireguard` config — is named in one `ALWAYS_ON` list in `NetworkData.js`. **That profile is currently absent** (deleted 2026-09-13; the tunnel moved to the defguard client, which NM doesn't own), so as of now `ALWAYS_ON` matches nothing: no Homelab section, no down-warning. The list, and the routing note below it, describe how it behaves when an NM profile by that name exists (by NM *connection* name, the only name the rows carry); it gets its own section, a red **down** marker, and the warning line. The `~/VPNs/*.ovpn` profiles are HackTheBox/TryHackMe labs and fall into "Labs". **The two overlap in 10/8 and the lab wins by default:** the homelab peer's `allowed-ips=10.0.0.0/8` installs one `10.0.0.0/8 dev wireguard metric 50` route, while HTB's openvpn pushes `10.10.8.0/22 via 10.10.14.1 dev tun0` — which *contains* the homelab's own `10.10.10.0/24`, and longest prefix beats metric, so with a lab up every homelab packet goes down the lab tunnel (`ip route get 10.10.10.1` names the device that actually wins). The profile therefore carries an explicit `ipv4.routes 10.10.10.0/24`, a longer prefix than the lab's /22. The cost is that HTB's legacy 10.10.10.x machines are unreachable while the homelab is up — `nmcli con down wireguard` for those. DNS needs no tunnel: homelab names are public records under `zarz.org`, so the profile's `ipv4.dns` is deliberately `1.1.1.1,1.0.0.1` and `ipv4.dns-priority=-50` is there only to stop eduroam's DHCP resolvers from replacing that list. The route edit is a `doas nmcli con mod <uuid> +ipv4.routes 10.10.10.0/24`: unprivileged `con mod` on a system connection silently destroys the stored private key. **Enter only ever connects, `d` disconnects**, for every row kind: toggling on Return put the always-on tunnel one stray keystroke from being dropped. (3) Nothing elevates — `con up`/`con down`/`device wifi connect` and `con import` are all fine unprivileged (`nmcli general permissions` lists `settings.modify.system` as yes). The menu runs `con mod` in exactly one place, the import above, and only against a profile it created one line earlier: unprivileged `con mod` drops a profile's stored secrets, but a fresh openvpn import has none — the certs are extracted to `~/.local/share/networkmanagement/certificates/nm-openvpn/*.pem` and referenced by PATH, so `vpn.secrets` is empty. Never `con mod` an existing profile (that is what destroys the wireguard private key). (4) NM connections are acted on by **UUID**, never by name (`con up id <name>` is ambiguous — several connections may share a name), and a VPN row whose *device* reads `connected (externally)` is labelled **external**: that is NM describing a `wg-quick` link it merely assumed, backed by a volatile profile in `/run`, not a profile you saved. (5) Wi-Fi, the radio and ethernet are native `Quickshell.Networking`: joining is `WifiNetwork.connect()`, which reuses the saved profile for that SSID (eduroam's is named `eduroam [a8f5604d]`, so matching by connection name would miss it). NM asks for a key by *failing* with `NoSecrets`, so a PSK network grows a password field in the bottom bar and retries once with `connectWithPsk`. The wifi device's `scannerEnabled` is bound to the menu being open. (6) The VPN half is still one tagged `sh -c` nmcli snapshot (connections + device states, ~25ms), `running: root.open`, so a closed menu costs nothing. nmcli's terse output escapes `:` as `\:`, so the parser unescapes rather than plain-splitting.
