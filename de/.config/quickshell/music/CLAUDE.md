# Music player (`de/.config/quickshell/music/`)

Loaded when working in this directory. MPD itself (config, MPRIS bridge, media keys) is in the root `CLAUDE.md` under **Music: MPD**.

A native MPD client in a **window**, not a picker overlay — `Super+W` / `qs ipc call music toggle`. Feature key `music` in the settings menu.

**Why a window.** `FloatingWindow` is an xdg-shell toplevel, so reach tiles it like kitty. Two things that cost time to find: (1) **`app_id` is `org.quickshell`** and there is no per-surface override — it is the process's. A reach rule matching that app_id is therefore exact only while this is the shell's only toplevel; narrow by title if a second appears. (2) Qt draws **client-side decorations** by default — a grey titlebar with min/max/close, on a desktop where kitty hides its own. `QT_WAYLAND_DISABLE_WINDOWDECORATION=1` in `~/.local/sv/quickshell/run` turns them off; harmless to the layer-shell surfaces, which never had decorations.

Lives in its own subdirectory, `de/.config/quickshell/music/` — 22 QML files, ~2.9k lines. That folder carries a **`qmldir`**, and it must list EVERY component: adding one turns the directory into an explicit module, which replaces the implicit directory listing, so anything unnamed stops resolving — including between files in that same folder. What makes it necessary is the two `singleton` entries (`MpdClient`, `Ui`): Quickshell auto-registers singletons in the config root but not in a subdirectory. A file that uses root-level `Txt`/`Field`/`Theme`/`Config` carries `import ".."`, since a QML file does not see its parent directory implicitly; one that uses none of them must not, or lint fails it as an unused import. `shell.qml` does `import "music"`.

**`Ui.qml`** is the folder's own singleton for sizing and pointer state: `Ui.s()`/`Ui.fs()` (the 1.2 font scale on top of `Config.s()`), `Ui.hs()`/`Ui.hfs()` (a further `headerScale` of 1.3, used only by `MusicHeader` and the tab strip — at list size they read as chrome rather than as the now-playing display), `Ui.rowH`, and the hover guard. All three were per-file copies before — a `fontScale: 1.2` property plumbed through ten files and never set to anything else, and the same ten lines of pointer-baseline state in both list implementations. One baseline for the whole player is correct rather than merely shorter: there is one pointer, and only one list is ever on screen. `MusicController.qml` deliberately does **not** use it (it imports nothing but QtQuick so the test suite can load it standalone).

**`MpdClient.qml`** — the protocol, spoken over a socket. Not `mpc`: every query would be a fork, and the interesting ones are not one-shot.
- **Transport.** Quickshell's `Socket` is a `QLocalSocket` — **unix only, no TCP** — so rmpc's port 6600 is unreachable from QML. MPD 0.24 opens `$XDG_RUNTIME_DIR/mpd/socket` by itself, which is the whole reason this needs no `mpd.conf` change. On an older MPD it would need `bind_to_address`.
- **Two connections, deliberately.** `idle` blocks its connection until something changes, so a client idling on its only socket can never ask a question. `idleSock` parks in `idle`; `cmdSock` carries commands (FIFO, one in flight, callback queue behind it).
- **Queue cost.** `playlistinfo` on a 6k-song queue is ~78k lines / 1.8 MB / ~180 ms, so it is fetched once and never polled. Edits ride `plchangesposid <version>` (see **Queue sync** below); a gap it cannot express falls back to a refetch. Measured: `lsinfo` 2.4 ms, `listplaylists` 0.1 ms, `search` 25–45 ms — all read-on-demand, nothing cached.
- **Volume is coalesced and predicted.** `↑`/`↓` are MPD's own volume, not Pipewire's, and MPD reports it back only through the idle loop (`mixer` → `status`) — so the readout trailed the keypress by a round trip, a held key computed each step off a number several presses old and lost most of them, and 50 `setvol` round trips a second queued behind each other on a FIFO socket, which is the *audible* lag. `volume` now returns what was asked for until a `status` carrying that value arrives (a 1s timer releases it if MPD never honours the write), and the writes flush at most one per 60ms.

**Seeking is coalesced and clamped.** Key repeat is 50/s, so one `seekcur` per press floods the connection. Repeats collapse into one absolute seek per 90 ms, the local clock moves immediately, and replies are ignored for 500 ms after (`_seekGuardUntil`) or the bar flickers between the key and the round trip. **The clamp matters: `seekcur <duration>` completes the track and MPD advances.** Worse, **MPD advances the track whenever a seek FAILS**, and a damaged file whose decoder cannot seek near its end fails every time — holding the key then walked the queue a song a second until MPD 0.24.12's output thread died on `Assertion nbytes % out_audio_format.GetFrameSize() == 0`. Hence a 5 s tail guard, a dedupe on the last position sent, and an ACK handler that halts the seek and resyncs.

**`MusicController.qml`** owns all state and keys; `MusicView.qml` composes; `MusicHeader/Queue/StatusBar/Overlay/Banner.qml` present. `MusicRowChrome.qml` is the row background shared by the queue's delegate and `MusicRow` (selection band, playing-song wash and accent, marked tint, guarded hover), and `MusicCrumb.qml` is the header strip over Directories/Playlists/Lyrics. `MusicList.qml` is the browse list under Directories, Playlists, Search and the C-a picker — cursor, navigation keys, `settle(keep)` after a re-read, and the `status` those panes show — and its `MusicRow` delegates route a double-click through the list's own `activated`, the signal Enter raises, so a pane wires activation once. `MusicPromptField.qml` is the prompt + field + placeholder used by the Search tab (`tag ›`), the picker (`name ›`) and the queue search (`/`); its `field` is the inner `Field` (bind `field.focus`, call `field.forceActiveFocus()`), and its keys come out as `keyPressed(event)`. `MusicEmpty.qml` is the centred empty-state line. The header's album art comes from the MPRIS bridge's cache, which **outlives the queue** — it is gated on MPD having a current song, or clearing the queue leaves the last cover sitting beside the word "Stopped". Panes take an injected `client`.

**The queue's model is a `ListModel` used purely as a row COUNT** — delegates read their song from the array by index. This looks redundant and is not, and all three variants were tried: an **array** model resets on every assignment (and every queue edit assigns, since QML only notifies on assignment), so even reordering flickered; an **int** model (`queue.length`) fixed reordering but still resets when the count changes, which is exactly what deleting does; only a `ListModel` takes insert/remove as **incremental** operations, leaving rows above the edit untouched so the scroll offset simply stays. `syncRows()` diffs old against new by song `Id` via common prefix/suffix. Measured with the cursor at row 3000: `contentY` 77234 before and after a delete, against 0 with the older models.

**`U` rescans the library** (`update` — changed files only, not `rescan`), for songs added on disk while the player was running. Deliberately **not** `C-u`: that is half a page up in every pane. rmpc has the identical collision — its defaults bind `<C-u>` to both `Update` (global) and `UpHalf` (navigation) — and resolves it the same way, by letting navigation win, so there is no rmpc key to copy here. The banner says "Scanning the library…" on the keystroke and "Library updated" when `database` arrives, which is a separate event some seconds later.

**Tabs** are rmpc's five, `1`–`5` and Tab/S-Tab (the strip prints names only; the digits still switch). Panes are built on first visit and kept, so a browse position survives a trip to the queue; a tab never opened is never built. Queue keys are routed only on tab 0 — otherwise `d` would delete a song that is not on screen. **The visible pane gets first refusal on every key**, ahead of the global playback bindings, which is what lets a tab own a key the globals also use (`i` is insert mode on Search and the info overlay everywhere else). That only works because every pane guards its modifiers — `h`/`l` but not `H`/`L` — so the globals still fall through.
- **Directories** — one `lsinfo` per level, never a recursive walk. It **reloads the level in view on MPD's `database` subsystem**, keeping the cursor (descending is what should take you to the top; a background rescan is not). `database` fires only when a scan actually changed something, unlike `update`, which fires when one starts *and* stops — so this is not a reload per keystroke. Without it the browser showed whatever was there when the tab was first opened; `add` on a directory URI queues everything beneath it, so no recursion here either. Sorted **newest first** by the directory's `Last-Modified` (which MPD derives from the songs under it), matching rmpc's `directories_sort: ModifiedTime(reverse: true)`. Folders only — inside an album the files stay in track order. **`A` at the library root queues the entire library** — `add ""` is MPD's whole database. That is rmpc's AddAll and it is wanted here (queue everything, then shuffle), but it appends rather than replaces, so pressing it twice gives you the library twice. A guard that refused it at the root was tried and removed.
- **Playlists** — two levels in one pane. `rm` is not reported as a queue change, so the list is re-read rather than waited on. `D` deletes the playlist (top level only), `d` removes the song under the cursor from the open one — `playlistdelete` takes a **position**, and the row index is it, since `listplaylistinfo` returns the playlist in order and carries no `Pos`. Saving the queue moved to **`C-s`**, because `C-a` became the add-to-playlist picker everywhere.
- **Add to a playlist (`C-a`, any tab)** — `MusicPlaylistPicker.qml`, a modal over the window rather than a pane, since the queue's selection (marked rows, else the cursor), a directory, a search hit and a playlist's song all raise the same chooser; a tab supplies its own `selectionUris()` and Lyrics falls back to the playing song. It is one `playlistadd` per URI: **a directory URI adds everything beneath it** (checked against MPD 0.24, same as `add` does to the queue) and **a name that does not exist is created**, which is why the "new playlist…" row is a text field rather than a second command path. That row sits **last** so the cursor opens on a real playlist — Enter should not reflexively start typing a name. **It is built by a `Loader` and destroyed on close, and that is the fix for a real bug, not tidiness:** a hidden `FocusScope` still holds `focus`, so `MusicView`'s `forceActiveFocus()` delegated straight back into the invisible picker and every key after an add — `j`/`k` on *every* tab — went nowhere. The search field's `leaveField()` is the same trap for the same reason.
- **Search** — matching is **MPD's**, server-side, case-insensitive substring (rmpc's `Contains`). Unlike the launcher's file mode there is no index to build. Debounced 180 ms, and a stale reply is dropped by comparing the query/tag it was sent with. **Modal, like vim:** the tab opens in normal mode, so `1`–`5`, `j`/`k` and every global key still work on it; `i` or `/` enters insert mode and the field takes the keyboard, Escape hands it straight back. It used to grab the field on arrival, which made the number keys type digits instead of switching tabs — and Escape could only leave the field when there were results, or the whole tab was a trap with no way out.
- **Lyrics** — `.lrc` beside the track, read from disk (MPD serves audio, not arbitrary files): `file:` is relative to `~/Music`, same basename, extension swapped. All 3,523 sidecars here are `[mm:ss.xx]`-tagged, so it follows playback; untagged lines keep order and never highlight.

**The banner** (`MusicBanner.qml`) fires on the queue **growing**, not on each add action reporting itself — so it also covers `load`, and adds made from rmpc or `mpc` while the window is open. It keys off **net** growth because reordering removes and re-inserts the same span. The first non-empty queue is suppressed (`_primed`) or the initial 6k-song load would announce itself. The other half of that suppression is `MpdClient.queueWasBulk`, and it means **"this was a first read"**, not "we refetched" — a distinction that cost the banner outright once. `syncQueue` refetches whenever it cannot express a change incrementally: more than 64 new ids, or any add at all onto an empty queue. Both are real adds, and `Shift+A` on the library is both at once, so `refreshQueue(false)` marks those fetches as edits while the open and reconnect paths keep the default. Verified by probe: a 1-song add onto an empty queue and a 118-song folder both announce.

**Queue sync uses `plchangesposid`, not `plchanges`.** An edit anywhere renumbers every song after it, and `plchanges` answers with FULL records for each — measured on this 6k queue, a change at position 0 returns **110,126 lines / 2.67 MB / 250 ms**, identical to `playlistinfo`, i.e. exactly the refetch it is supposed to avoid. The `posid` form answers the same question as `cpos`/`Id` pairs: **12,379 lines / 129 KB / 25 ms**, 20× smaller. Since the metadata is already held keyed by `Id`, a pure renumbering costs zero extra reads; only genuinely new ids are fetched (one `playlistid` each, batched, falling back to a full refetch past 64). *(rmpc does not do this — its binary contains `playlistinfo` and no `plchanges` at all, so it refetches the whole queue on every change.)*

**The queue is refcounted, not permanent.** It is the one expensive thing the client holds — 6k songs is ~110k protocol lines parsed into 6k objects — and nothing needs it while the window is shut. `retainQueue()`/`releaseQueue()` are driven by the window's Loader: released on close, refetched once (~250 ms) on open, and the idle loop stops syncing a queue nobody is reading. The sockets stay up, so transport and now-playing keep working regardless.

**The command socket is kept alive by a 30 s `ping`.** MPD's `connection_timeout` defaults to 60 s and `mpd.conf` does not set it, so `cmdSock` — which sits silent between commands — used to be closed by the server roughly once a minute (`QLocalSocket::PeerClosedError` every ~66 s in the quickshell log), and the 5 s retry timer reconnected it. That is not free: the greeting on the new connection runs `refreshAll()`, which **refetches the whole 6k queue** while it is retained, and resets `queueWasBulk`. A `ping` on a 30 s timer, gated on `root.connected`, keeps the connection well inside the window instead — two five-byte commands a minute against a 250 ms refetch. `idleSock` needs none: MPD does not time out a connection parked in `idle`, which is also why only one of the two ever churned. It had always done this; it only became visible once the window was left open for hours.

**Gotchas worth remembering.** `MpdClient` is a **lazy singleton** — nothing talks to MPD until the window is first opened, which is good for RAM but means `reset()` runs against an empty queue (hence `_jumpPending`, and a deferred reveal because the view has not laid out in the frame the model goes 0 → thousands). Quickshell's QML **hot reload goes stale**: edits silently stop applying, so `SVDIR=~/.local/sv sv restart quickshell` before concluding a change did not work.
